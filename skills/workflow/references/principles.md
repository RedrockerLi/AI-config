# 协作原则

多 agent 的价值来自扩大有效认知和行动的范围。它也引入新的接口、上下文副本和接收工作。判断协作时，同时看它解除了什么约束，以及把成本和不确定性转移到了哪里。

下列四个视角共同解释同一项工作，阅读顺序不代表执行顺序：

- [依赖与有效并行](#依赖与有效并行)：认知范围、关键路径、持续接收和资源。
- [契约与决策边界](#契约与决策边界)：共享含义、局部自主与相互牵制的取舍。
- [知识与工作状态](#知识与工作状态)：上下文、证据、版本与接续。
- [反馈与整体交付](#反馈与整体交付)：增量、验证、完成与协作效果。

## 依赖与有效并行

### 认知扩展与行动重叠

独立上下文可以让参与者在不同资料、假设或问题局部上持续深入，再把有用结论交回整体。它扩展的是有效认知范围，不只是同时生成更多文字。单个上下文需要来回切换大量细节时，有边界的委派可以减少干扰；问题需要频繁共享中间推导时，切碎它反而增加理解负担。

认知扩展与行动重叠是两种收益。几次相互独立的检索或执行可以直接并行调用工具；需要独立选择调查路线、判断证据或承担持续责任时，增加 agent 才有额外意义。分工不同、来源不同或实验条件不同，可能带来互补信息；换一个角色名、复制同一上下文，并不保证新的视角。

收益还取决于困难来自哪里。真实状态和例外之间的复杂关系，可能需要更好的抽象或数据表示来减少；外部协议、业务规则和使用习惯，需要查明真实约束后适配；不断变化的环境，需要能吸收变化的边界；难以观察的行为，需要结构、数据流、时序和真实运行等互补证据。根据这些差别安排调查和实施，才能让新增能力触及瓶颈。无价值的规则可以在授权范围内简化，已有外部承诺仍需守住。

改善工具、抽象或复用成熟组件，有时可以直接消除一层工作。更快生成代码只改善完整流程的一部分，其他环节仍可能限制交付。依据可比任务的实际结果判断收益，保留新能力改变瓶颈的可能，不把某种工具或“多 agent”本身当作效果保证。

### 关键路径与持续接收

区分总工作量、完成历时和吞吐。总工作量包括理解、设计、执行、协调、验证、集成与返工；历时受关键依赖链及资源等待约束；吞吐受最慢的接收环节限制。以少量额外成本缩短关键历时可能值得，以大量并发制造等待中的产物则可能没有收益。

分解时寻找能提前解除依赖的最小有用结果。一项调查尚未完成，已经确认的兼容限制也可能足以让实现开始；一条真实路径已通过，其他路径的调查仍可继续。传递这个结果时说明哪些已经成立、哪些仍是暂用假设，以及什么新发现会使它失效。在稳定承诺内，设计细化、实现和工具准备可以重叠。等待范围由下游所需的前提决定，也要考虑分批接收的成本；整组结果共同成立才支持行动时，等待整组是必要的。

委派后，发起者可以继续处理尚未分出的关键路径、准备接收与验证，或解决跨域问题。重新做一遍已交出的调查，往往同时失去并行收益和独立视角；若确实需要独立复核，应有明确的风险与不同证据。必要依赖尚未返回且没有有用的独立工作时，等待是合理选择。

接收可以随着结果到达持续进行。得到足够可靠的局部结果就解除对应依赖，同时保留尚未覆盖的验收范围。收到报告、完成核验、允许下游依赖是不同状态；报告先到不代表其方案更优。运行环境支持怎样的消息和结果交付，就据此安排重叠，不假定每种工具都支持中途回传或中断。

探索会改变分工。新证据可能让原本独立的任务合并，也可能从一个瓶颈中分离出可并行的工作。某条路线已被证据排除、与已完成工作重复或不再影响交付时，及时缩小、改派或结束投入，交代已有产物和在途操作。结束可选探索前，确认它没有承担尚未覆盖的必要验证；必要工作可以换人完成，不能借取消而消失。

增加参与者会带来上下文构建、重新分配、协调、结果检查和集成成本。复制上下文可能让启动很快，但验证、共享环境竞争和语义同步并不会消失。越接近交付，剩余收益窗口越小；新增工作应能真正解除当前约束，避免同时引入无关重构或全新的协作流程。

新增 agent 的价值取决于它带来的边际能力。如果任务独立、交接成本低、接收者有容量，晚期并行仍然可以有益。若它只能重复已有轨迹或争用同一资源，增加人数可能延长交付。全员互相了解全部细节会增加沟通关系；减少必要依赖比优化每条消息更有力量。

依赖图的价值是澄清谁等待什么，并据此识别关键路径和可用余量。局部延迟不一定影响交付，但微小延迟的累积会吃掉余量。随着证据改变，重新判断关键路径；无需为很小的任务维护复杂图表。

估算应参考范围、环境、模型能力和质量要求相近的已交付工作，包含真实等待、失败重试和接收成本。简单样例的生成速度、代码行数、token 数或瞬时并发量，都不能直接外推出系统交付速度。明确估计区间及其假设，用代表性切片校准。

计划日期表达协调后的目标，估计日期表达现有条件下的判断，实际完成需要证据。期限压力不会使必要工作自动消失。重新计划时容纳已暴露的原因与不确定性，避免反复作出同样欠充分的小幅顺延；若需要改变用户承诺，明确提出取舍，取得相应授权。

### 全局资源与接收能力

预算要联系功能和服务水平，并包含所有参与者的累计消耗。上下文容量、推理成本、工具次数、运行时间、内存、外部配额以及验证容量，哪些重要由任务决定。为探索、集成、排障和必要返工保留容量，不把所有资源都分配给首次生成。

局部指标可能把成本推出边界。一个 agent 通过省略依据缩短报告，会把核验工作交给接收者；一个模块通过把缓冲或重试交给调用方满足局部限制，可能增加整个系统的成本。评价优化时追踪成本去了哪里，以及整体行为是否仍然符合用户目标。

资源之间可以交换，关系也可能非线性。更大的上下文、更强的工具或更多缓存有时值得投入，也可能增加噪声、延迟或维护成本。让有代表性的测量支持取舍；单独追求最少资源或最多并发都容易偏离目标。

共享测试环境、数据库、构建服务或外部系统可能在集成时突然成为瓶颈。对影响彼此结果的操作协调使用范围与时段，必要时隔离工作副本；对有前后状态关系的实验，连续稳定的使用窗口可能比交错争抢更有效。具体做法取决于真实冲突，无须套用固定时段。

接收速度也是资源。产物积压意味着上下文会过时、冲突会累积、反馈会延迟。此时可以缩小在途工作、加快接收，或让已完成的参与者帮助验证真实边界。合理的空闲好过制造没有接收能力的新工作。

## 契约与决策边界

### 共同用户模型与概念完整性

一致的设计首先依赖对用户的共同理解。不同 agent 可能分别假设用户是新手、专家、管理员或程序调用者，并各自做出合理却互不兼容的决定。让目标用户、实际需要、提出的期望和主要使用情境变得明确；暂时不知道的部分可以作为假设保留。

使用频率也会影响设计。常用路径与少见能力如何分配复杂度，需要共同依据。没有测量时，把频率判断标为估计，考虑结论对估计是否敏感：若换一个合理数值就会改变方案，优先获取更可靠的资料或进行小规模验证。其他 agent 对该估计的转述不会提高它的可信度。

概念完整性体现为可预测的行为和一致的取舍。共享术语、错误语义和交互习惯能让使用者迁移已有知识。评价设计时，同时考虑它提供的功能与理解这些功能的成本。概念少却要求复杂组合，也可能难以使用；功能多却使普通任务绕远路，同样损害整体价值。

类比、已有约定和使用示例可以成为分工双方的共同语言，但要说明类比在哪里失效。例如，分别负责易发现入口和熟练用户快捷方式的 agent，应共享操作的实际含义，再自主选择呈现方式。这样，一种入口验证过的语义可供另一种入口依赖，用户也不必学习两套相互冲突的系统。

共同概念需要连贯的设计责任，能够把功能、性能、规模、成本和时机放在同一用户目标下权衡。责任可以属于一个参与者，也可以按稳定领域分布。实现者与使用者都能贡献设计；裁决要解释相容性和依据，职位、投票或集中程度本身不能保证正确。

新版本尤其容易积累过去搁置的想法，以及各个 agent 提议的通用机制。每个选项都有理解、组合、验证与维护成本。用当前需要和可验证收益决定投入；当系统的基本目标已经改变时，也应重新审视对旧机制继续精修是否值得。尚未实现的新构想不能仅凭吸引力取代已经满足目标的成果。

### 契约让独立工作能够组合

契约规定其他部分可以依赖的行为，也明确尚未承诺的行为。输入输出的含义、失败如何表达、状态归属、时序条件、兼容性和资源约束，往往比函数名称或数据格式更重要。把这些含义说清，才能把内部算法和组织方式交给局部实现者自由决定。

设计者应理解重要承诺至少如何可行地实现，并听取实现成本的反馈。可行方法用来支持设计判断，不必变成唯一实现。若实现者发现更好的方式，按契约与整体成本评价；若契约本身导致不可接受的代价，就回到共享设计调整承诺，而不是要求局部工作无限补偿。

自然语言可以解释原因与边界，类型、模式、示例和可执行检查可以提高精确度。对每项承诺明确权威定义，其他表达与其保持一致；冲突暴露的是需要解决的问题。共享定义能直接复用时，尽量减少逐份转写，但相同类型仍不能保证相同语义。

以现有实现作为兼容依据时，区分用户依赖的行为、明确保证的行为和偶然副作用。探索这些差别需要证据。不能自动把所有现状升为契约，也不能把已有依赖随意归为“实现细节”而删除。兼容验证所依赖的实现版本应清楚。

边界两侧可以直接用具体输入、失败和反例澄清理解。契约内的配合由双方自主完成；涉及公共解释的答复进入权威定义，并送达其他受影响者。事实不必逐层转发，但当前完整承诺不能只存在于一次私下对话中。

当契约存在歧义或需要支持多种实现时，独立的使用者、实现路径或契约测试可以暴露单个作者忽略的假设。投入范围取决于风险；目的在于检验外部行为的独立性，无须为每项功能制作多套完整实现。

### 分解、责任与取舍依据

从目标和数据含义逐步精化责任，在当前层次使用足够表达问题的抽象。稳定的语义边界、变化来源和可独立验证的结果，是分解的依据。按文件平均切分，只解决了一种写入冲突；不同文件仍可能依赖同一状态或语义。反过来，同一个领域也可能容纳独立的事实调查、实验与验证。

信息隐藏让边界另一侧可以独立变化。把易变的内部决定留在局部，把稳定含义公开。边界两侧持续联动时，查找尚未显式化的共同决定；可以把它上提、合并紧密耦合的工作，或重新划分。当前的组织结构应能随设计改变，而不是迫使产品适配已有角色。

委派时提供目标、背景、约束、必要依赖和完成依据，让参与者自己选择方法、调查未知并提出改进。有时交付物是实现，有时是一次否定假设的实验。过度规定中间动作会占用负责人的注意力，也会阻止最了解局部证据的 agent 作出判断。

决定归属随影响范围划定。只影响本地产物、能低成本撤回且未改变承诺的选择，可以自主试验；改变他人输入、共享资源或用户目标的决定，需要覆盖这些影响的责任与沟通。两位参与者能在各自授权内解决边界问题，就直接协调；超出授权或有无法兼容的取舍时，再扩大裁决范围。

连续推理与任务拆分之间，比较的是独立发现的收益与重建中间状态的成本。若双方每一步都需要对方最新推导，保持问题完整通常更有利；若只需要少量稳定输入，独立上下文可以深入各自的证据。把调查和实施拆开、让一人维护共同模型而其他人寻找反例，也可能比按模块切开更有效。

稳定契约与快速反馈之间，判断未知是否会改变当前行动。可能推翻大批后续工作的未知，值得先用实验解除；只影响局部且可逆的未知，可以在明确假设下推进。已经被证据否定的契约需要修订，保留仍有效的部分，并让依赖者知道哪些结果必须重做。这些判断不要求预先冻结全部设计。

组织推进与保持技术一致性是两种责任。它们可以由同一个 agent 承担，也可以拆开；拆开时要让优先级、资源安排与设计取舍能够协调。事实沿依赖直接流动，裁决归属仍需清楚，避免同一公共承诺受到相互矛盾的指令。

保护高耦合问题的连续推理，让独立调查、工具维护、测试数据或文档整理解除具体负担。每项辅助工作应有真实产物与接收者，无须复制固定的职业名录。规模扩大时，可以把稳定子领域连同判断权交给局部负责人，使上层关注跨域关系。

能力应由任务表现、可用证据和环境决定，角色名称不能制造专长。对关键概念投入足够推理，对明确而重复的工作采用合适工具；发现不匹配时调整责任。保护连续推理、改善反馈环境能减少上下文重建和工具等待，但不能据此假定 agent 具有人类团队相同的资历、情绪或效率规律。

## 知识与工作状态

### 权威定义与按需上下文

共享上下文的目标是让参与者足以作出正确决定。共同目标、接口语义、当前版本和关键约束应容易取得，内部细节按依赖深入。精简上下文时保留能改变结论的前提、反例和证据入口；若摘要无法回答当前问题，就回到原始材料。检索或加载更多信息的成本，应与猜错后返工的成本比较。信息隐藏保护局部变化，相关证据仍应能供排障与审计取得。

共享记忆宜由少数有明确用途的材料构成：当前承诺、关键决定、责任与依赖、结果证据。书写的价值在于暴露分歧和补全尚未作出的决定；篇幅与文件数量本身没有价值。记录要能发现、检索和维护，避免每个 agent 各存一份失去同步的“当前真相”。

让参与者能分别回答“现在有效的定义是什么”和“自我上次读取后，哪些变化影响我的工作”。稳定的当前说明与简短的变更通知承担不同作用。通知应指向受影响的契约、决定和验证，而不是广播每项局部细节；重要变化需要确认已进入相关下游的判断。

每个上下文都是可能过时的副本。新证据否定某个假设后，找到仍依赖它的工作，修订共同依据，通知相关参与者并重新判断既有产物与检查的有效性。关键变更需要确认下游理解了影响，而不仅是消息已送达。异步到达的旧结果按其基线检查，不能覆盖较新的决定；有用的部分仍可吸收。不同 agent 使用同一段文字，也可能赋予它不同含义，可以通过具体输入、预期行为和反例核对。

摘要是有损压缩。交接结论时，保留决定、原因、适用条件、原始证据的位置和未决问题，区分观察、推断和建议。代码、数据和详细结果可以直接保存为可定位的产物，让接收者引用与核查，减少逐层转写中的丢失。嵌套委派越深，越要防止条件和异议在综合时消失。多份报告引用同一来源，仍然只有一份来源。

替换参与者或跨上下文接续时，显式传递实际工作状态：使用的基线、已经修改的产物、验证范围、未完成依赖以及仍在运行的操作。接手者据此恢复判断，而不是从一句“基本完成”推断结果。角色迁移与恢复上下文也有成本，不能把整段探索经验视为能免费复制；持久记录也不意味着模型本身已经永久学会了这些内容。

### 共同工具、复用与表达

共同工具和约定减少重复探索及交接摩擦。维护可靠的基础能力，使参与者可以用一致方式理解输入、运行检查和解释输出；局部专业工具仍可按问题需要选择。工具维护和环境修复应有实际责任，但无须因此设立永久的独立角色。

把任务特有的领域事实和规则，与可复用的执行、推理机制分开维护。诊断经验可以形成有依据的规则与案例，但其价值取决于知识的准确性和适用条件；当组件或契约变化时，相关规则也要重新判断。更复杂的推理流程不能补偿缺失的领域知识，提取和核实这些知识本身也需要投入。

缩短“提出问题—执行—观察”的周转有助于保持推理连贯。执行前明确要区分什么，执行后解释异常、更新判断和保存关键证据。快速工具支持更多试验，但盲目重试仍可能只是更快地产生噪声。环境本身不稳定时，先区分环境问题与被测对象的问题。

更高层的表达可以消除无关细节，使注意力落在领域概念与真实约束上。可靠的类型、结构化控制、共享声明和成熟组件能减少容易出错的手工工作。性能等约束确实要求更低层实现时，用测量定位值得细化的部分。技术名称和语言选择本身不能保证良好设计。

数据表示常决定算法和协作方式。如果各路工作不断补偿相同的含义混乱，重新表达状态、数据或领域边界，可能比增加协调与转换更有效。在实现局部优化之前，允许重新检查问题的表达。用结构、数据流或时序等视图传递各自擅长说明的关系；逐行重画代码增加同步负担，单一视图也不足以代表全部行为。

先考虑已有能力能否直接使用、配置或组合。复用可以省去整层设计与验证，但仍有查找、理解、适配、运行和维护成本。看起来能运行的片段不等于可靠组件；通用组件需要明确的适用范围、稳定接口、足够的检查与文档，其初始投入应有可预期的复用价值。

复用的瓶颈也可能在发现和理解。统一领域词汇、按功能检索、展示完整组合示例，常比继续扩大组件数量更有帮助。让使用者看到语义、限制和组合方式，无须预先记住整个工具库。把某项技术引入团队时，传递其设计原则与实际例子，比只要求采用某种工具更有效。

把完整应用或外部工具作为组件时，核对控制权、输入输出和错误语义。交互式展示未必是可解析的结果，单独成功也未必允许外层可靠控制流程。尽量依靠明确的组合接口，使数据与状态能被下游理解；必要的适配成本仍属于整体成本。

### 文档、维护与知识积累

维护包括修复缺陷、适配环境和回应使用反馈。新用户、新数据和更深的使用方式会暴露旧检查没有覆盖的情况。局部修补可能改变其他行为，需要按影响范围做回归；若联动修改不断扩散，重新检查边界和共同模型，而不是无限叠加补丁。

把文档视为 agent 之间可恢复的工作接口。接收产物的参与者需要据此判断环境、有效范围、输入输出、异常行为和资源或精度限制；继续修改的人需要恢复结构、数据流、关键算法、依赖与取舍原因。缺失这些信息会把作者节省的时间变成接收者的猜测和重复调查。内容深度由实际使用与维护需要决定，放在最合适的权威位置。

名称、类型、声明和清晰结构能承载许多信息；说明补足代码无法表达的意图、限制与原因。重复逐行解释代码会增加同步负担。保持说明与实现靠近、引用共享定义，给读者提供整体概览和必要细节的入口。文档描述当前有效状态，历史决定仅在理解当前约束时需要追溯。

可复现的使用与验证示例帮助接收者确认环境和产物是否匹配。已知限制、未决问题和临时处理应有清楚的位置，使下一位参与者无需重新发现。文档量应随实际使用和维护需要增长，能指导正确行动比篇幅更重要。

经验积累应保存可检验的机制：问题出现的条件、证据、有效做法及适用边界。共享这种材料、工具和组合实例，可以减少后续任务的重复理解。一次成功不必成为普遍规矩，一次失败也不必永久增加一道审批或固定阶段；根据复现、使用反馈和环境变化继续修订。

## 反馈与整体交付

### 完整结果与用户价值

程序在作者的环境里运行，产品能由其他人使用，组件能与其他部分组合，是不同的承诺。后两者还涉及输入边界、错误行为、兼容性、资源消耗、使用说明和可维护性。多个 agent 分别交出能运行的片段，未必交出了一个可用系统。

分配实现工作时，也要容纳产品化和系统化的工作。某项功能的完成证据应与承诺的使用方式一致：演示一条路径可以支持原型判断，供他人依赖的组件需要足以说明其适用范围的接口、验证和文档。简短任务可以有简短证据，复杂任务则需要承担实际的组合成本。

用户得到的价值取决于整体体验。速度很快但无法正确恢复失败、接口丰富但调用含义不一致，都可能使完整目标落空。实现责任、设计责任和用户验收各自看到的只是其中一部分，需要有人把这些判断放回同一目标中。

生成与交付之间的差距应由具体任务估算。固定的人力倍数、编码与测试比例、团队规模和缺陷概率，无法直接描述不同 agent、上下文和环境中的成本。

### 原型与持续生长

需求发现本身就是开发。用户与实现者可能要接触可观察的结果，才能发现遗漏或误解。探索应让重要假设受到检验；若缺少信息会改变目标或关键取舍，寻求用户的相关判断，同时推进不依赖该答案的工作。

原型回答一个具体问题。界面模拟可以检验理解，性能实验可以检验关键成本，受限环境可以验证可行性。结论限于它实际覆盖的条件：模拟输出不能证明功能已经存在，顺利路径也不能证明异常处理成立。是否保留实现取决于产品要求和补齐差距的成本。

增量产品与原型可以相互配合，也可以独立存在。一个闭环骨架可以先用占位组件检验连接，再逐步替换成真实能力；一段有限但完整的功能可以早期验证性能与使用体验。随时清楚哪些部分只是占位，哪些行为已经由真实组件证明。

让可运行、可验证的系统持续生长，尽早碰到真实接口、用户反馈和资源限制。一次增加多少内容，由定位问题和验证交互的能力决定。稳定部分可以展开并行，未知部分继续探索；无需等待所有组件齐全才开始整体学习。

反馈可以跨越多个层次。实现发现不可能满足的契约、测试发现需求误解，都可以促成设计甚至问题定义的修订。保留可靠部分，重做失效部分；整体推倒和严格单向阶段都不是必需的。进度压力也不能把未经产品化的实验直接升格为交付物。

面向明确的后续版本或产品差异时，把较稳定的决定放在共同基础上，让可能变化的部分能独立替换。中间增量也可按此安排，以减少回溯。预测是一种有条件的设计依据，无须为所有想象中的未来构建通用框架。

### 稳定基线与集成反馈

自由探索、集成候选和可依赖的已验证版本，需要有可辨认的状态。局部工作可以灵活修改；其他人用作依据的版本则需要明确的变更归属、可定位的内容和重新验证。具体载体可以不同，关键是接收者知道自己正在依赖什么。

共同工作空间意味着文字之外还有共享状态。文件、生成产物、运行进程和外部数据的并发修改，可能影响其他 agent 的证据。根据实际冲突明确写入责任或隔离范围，核对产物的基线。文件没有合并冲突，不能证明组合后的含义正确。

集成尽量以容易归因的增量进行。让组件具备相称的局部证据，再检验它与整体的关系。已知缺陷如果会干扰判断，应先处理或隔离；把缺陷写进报告，并不会使它对系统的影响自动消失。早期整体检验有价值，但它依赖对当前可运行范围的诚实说明。

可重复的构建和检查提供共同反馈。共享基线失效时，优先恢复这份共同依据，暂停继续依赖失效部分扩大集成；不受影响的独立工作可以继续。反馈频率由成本和变更速度决定，固定每天、每轮或每个参与者一次都不必成为规则。

临时补丁应与正式解决清楚区分，保留其原因、作用范围和后续责任。使测试暂时继续的修改还需要进入正式产物及相应验证。每次接收新版本都要重新判断受影响行为，避免一边移动基线，一边把旧检查当作当前证据。

### 独立判断与分歧

验证从承诺开始。提前考虑什么输入和观察能够区分正确与错误，常能发现规格中的空白。审查设计与要求本身，同审查代码一样有价值；再精确的形式化检查，也只证明给定假设与规格之下的性质，不能代替判断这些规格是否满足用户。

局部、交互、整体是不同层次的证据。常规输入、合法边界、无效输入、失败恢复和关键资源条件应按风险得到覆盖。测试替身、小型代表数据、仿真器和诊断工具可以降低反馈成本，但它们本身也有正确性与保真限制。稳定的模拟环境适合隔离原因，真实目标环境仍有它必须承担的验证。

独立检查的价值在于发现共享盲点。让审查者接触原始要求、实际产物和必要背景，先形成判断，再利用作者解释核对上下文。不同角色名不保证不同视角，相同模型、资料和问题表述可能产生相关错误。可以改变证据来源、关注的失效条件或实验方式，取得有意义的独立性。

出现多个解释时，把争论变成可区分的预测。一个能排除替代解释的小实验，可能比更多类似意见更有用。记录观察条件，防止同时改变多个因素造成错误归因；证据不足时保留多个解释，多个原因也可以同时成立。

审查结论是需要裁决的主张。把发现关联到要求、产物、机制或反例，判断其是否成立以及影响范围。作者和审查者都可能遗漏前提；多数票、信心和表达的流畅程度不能代替核验。成立的问题进入修复，被证据否定的发现可以关闭，尚不能判断的保留为未决。

反馈需要进入实际行动才产生价值。确认一个建议被采用，要检查相应的决定、产物或验证是否改变；回复“已理解”不能证明修改发生。预期输出、示例和计划是判断依据，真实工具结果与环境状态才说明执行了什么。必要时核对持久产物和运行记录，避免把完成叙述当成完成证据。

质量工作通过减少后续返工促进交付，投入仍应与风险相称。小而可逆的修改不必承担复杂系统的完整审计；高风险的共同假设值得更强验证。测试通过、审查无新发现都只支持其覆盖范围，无限追加同质审查也不能证明绝对正确。

### 真实进展、收敛与协作评估

进展体现为可以核验的事实：一个行为成立、一条依赖解除、一个关键假设被验证或推翻。里程碑应有清楚的完成边界，能够暴露仍缺什么。“基本完成”、产出字数、参与者数量和自报百分比都容易掩盖尚未发生的集成工作。

如实观察状态与决定是否干预是不同责任。让参与者报告发现、阻塞与失败，由承担相应范围责任的人判断其影响。局部可解决的问题可以继续由局部处理；跨域依赖需要及时协调。角色提示和汇报要求应容纳不确定与反例，避免把“成功交付”的期待变成只报告好消息的压力。

综合随着可用结果到达持续进行，判断相互关系、冲突和缺口。候选建议、已核验事实和正式接收的产物需要可辨认；这允许可靠部分先推动下游，也防止临时解释悄悄成为正式承诺。未返回的必要工作仍是缺口。相互不兼容的方案可以取舍，吸收不同方案的部分优点时，重新验证组合后的前提。

结束判断包括承诺的范围、整体证据和剩余风险的处置。可运行的增量可以支持有价值的部分交付，只有在其范围符合授权时才代表本次完成。降低要求、略去失败或把预算耗尽当成验收，都不能制造完成证据。

协作本身也接受反馈。观察真实任务中必要依赖等待了多久、重复调查和返工发生在哪里、结果何时被接收，以及最终质量和总消耗。轨迹应足以把结论关联到实际委派、工具行为、产物与验证，单靠参与者自述不能证明安排有效。

文字场景可以检验推理是否自洽，真实执行才能暴露消息延迟、写入冲突、环境竞争和接收瓶颈。评价结果应允许不同但有效的协作方式。若要声称某种安排更快或更可靠，需要在任务、工具、预算和质量要求可比的条件下比较，考虑模型与执行的波动；单次成功只提供有限证据。保留有效安排，合并没有独立价值的交接，把资源移向当前瓶颈。
